# 020：球员目录与比赛数据只读边界

## 当前状态（2026-09-08）

- 已新增 `supabase/migrations/020_catalog_read_only.sql`，没有修改已应用的 016–019。
- 本地隔离 PostgreSQL 的完整安全回归已通过；完整 Vitest 回归 **150 个文件、1650 项测试全部通过**（exit 0）。**生产库尚未应用 020**。
- `players` / `game_logs` 的生产风险只有在用户网页执行完成并复核后才算关闭。

## 修复范围

1. 撤销 PUBLIC、anon、authenticated 对两张表的所有既有表级及独立列级授权，之后仅给 anon/authenticated SELECT。
2. 开启 RLS，增加浏览器读取策略和服务端写入策略；保留 service_role 的导入能力。
3. 检查继承授权是否仍留下写入口，包含 PostgreSQL 17 的 MAINTAIN。发现残留即抛错、回滚，不静默宣告成功。
4. 保留 `get_random_log(text)` 返回 JSON 的接口和 SECURITY INVOKER 语义；固定空 search_path，并限定访问 `public.game_logs`。
5. 不修改球员/比赛数据行，不调整全局默认授权，不改动用户已有前端修改。

这些历史目录表由外部导入，不属于 001–019 的建表基线。如果两张表和 RPC 都不存在，020 明确提示并跳过，不创建空壳；只缺一部分则拒绝执行。未来新环境若再导入这些目录，应在对外开放前同步应用这份权限边界，不能依赖“迁移编号存在”判断导入后的表安全。

不需要数据库密码，不重置密码；仍由用户点击 Supabase Dashboard。

1. 核对项目 `hnhrpwwznzokkfagfumb`，main / PRODUCTION，SQL Editor 角色为 `postgres`。

4. 协作者检查快照和现有迁移历史，并用生成器创建只执行 020 的事务脚本：

```powershell

  --snapshot 'D:\文件\ReplayMod-before-020.csv' `
```

生成器拒绝缺少 016–019、已有 020/更新版本、异常对象所有者/策略/RPC、损坏或超过 24 小时的快照；不会覆盖已有文件。它不连接数据库。备份包含当前元数据，存放位置应限制访问。

5. 暂停目录导入，留出短维护窗口。确认目标项目后，在网页**整份执行生成的 APPLY-020-WEB.sql 一次**。不要自行拆分 SQL；不要直接执行裸迁移文件代替受保护脚本。如果网页建议自动追加 RLS，请保持原 SQL，不附加自动生成的策略。

数据库名 `postgres` 不能唯一标识 Supabase 项目；生成器/SQL 无法代替人工核对 Dashboard 的项目和分支。

## 备份与失败处理

- 本次是 ACL/RLS/RPC 元数据变更，因此先导出受影响对象的最新结构、授权、策略、函数定义及迁移历史摘要；**该快照不是数据备份，也不包含这两张表的数据**。
- 旧的 before-016-019 快照同样不包含这两张表的数据，不能拿其空壳覆盖生产表。
- 网页脚本在同一事务中锁定目标表及迁移历史，检查快照指纹，然后应用 020、记录 020、通知 PostgREST 并提交。
- 超时、结构/授权/角色/历史漂移或任一迁移错误都应中止事务。已测试末尾强制报错时表权限、RLS、RPC 及历史记录整体回滚。
- 已成功提交后不要用恢复原公开写权限作为自动“回滚”。若兼容性异常，应先保留只读边界，依据元数据快照定向修复服务端导入/读取权限。
